# Caser.one — Полная копия проекта (1:1 Клон)

Точная копия сайта игрового проекта **caser.one** (CS2 кейсы, апгрейд предметов, еженедельные награды и розыгрыши), выгруженная и развернутая с помощью автоматизированного инструмента парсинга и сборщика ассетов.

---

Драйвер БД: [`@libsql/client`](https://github.com/tursodatabase/libsql-client-js) — работает
одинаково с локальным файлом (`file:`) и с Turso (`libsql://`), поэтому один и тот же
код работает и локально, и в продакшене.

## 💾 Хранение данных

Баланс, инвентарь, история транзакций и лог открытий хранятся в **SQLite**.
Драйвер — [`@libsql/client`](https://github.com/tursodatabase/libsql-client-js), который
умеет два режима и поэтому один и тот же код работает локально и в облаке:

| Режим | Конфигурация | Когда данные сохраняются |
|---|---|---|
| **Локальный файл** | `DATABASE_URL` не задан → `DATA_DIR/caser.db` | Пока жив инстанс (Free — обнуляется при спиддауне/редеплое) |
| **Turso (облако)** | `DATABASE_URL=libsql://…` + `DATABASE_AUTH_TOKEN` | Всегда, независимо от перезапусков и деплоев |

- **Аккаунт выдаётся на первый запрос** и привязывается к cookie `caser_user_id`,
  поэтому у каждого браузера **свой** баланс и **свой** инвентарь.
- Если база недоступна — сервер автоматически откатывается в режим «в памяти»
  и продолжает работать (данные живут до рестарта).
- Ледгер: каждое движение баланса пишется в `transactions`
  (`GET /api/users/balance/history`).

### Настройка Turso (бесплатно)

**Самый простой путь — через веб-панель**, без CLI:

1. Открой <https://turso.tech> и зарегистрируйся (GitHub-аккаунт подойдёт).
2. В консоли нажми **Create database**, выбери регион (например `fra`).
3. Скопируй **URL** — он выглядит как `libsql://<имя>.turso.io`.
4. В меню базы → **Tokens** → **Create token** → скопируй токен.

Если хочешь пользоваться терминалом, CLI ставится не через npm:

```bash
# Linux / macOS / WSL
curl -sSfL https://get.tur.so/install.sh | bash

# или через Homebrew
brew install tursodatabase/tap/turso
```

> ⚠️ На **Windows без WSL** CLI не ставится — используй веб-панель.

Затем в Render → сервис → **Environment** добавь
`DATABASE_URL` и `DATABASE_AUTH_TOKEN`, либо запиши их в `.env`.
`store.js` сам определит режим по наличию `DATABASE_URL`.

> ⚠️ На Render **Free** файловая система эфемерная: при локальном файле
> база переживёт работу инстанса, но **обнулится** при спиддауне (15 мин без трафика)
> и при каждом редеплое. Только внешняя база (Turso/Neon) решает это полностью.

## 🚀 Деплой на Render

1. Запушь репозиторий на GitHub/GitLab.
2. В Render: **New → Blueprint** → укажи репозиторий (Render прочитает `render.yaml`).
   Либо **New → Web Service** с теми же настройками:
   - Build Command: `npm install`
   - Start Command: `npm start`
   - Health Check Path: `/healthz`
3. Проверка после деплоя: `https://<твой-домен>.onrender.com/healthz`

Переменные окружения: `DATABASE_URL`, `DATABASE_AUTH_TOKEN` (Turso), `DATA_DIR`,
`RTP`, `ADMIN_TOKEN`, `ADMIN_IDS`, `CASES_CACHE_DIR`, `REMOTE_CDN`, `NODE_VERSION`.
Подробности — в `.env.example`.

## 🏦 Вывод предметов и админ-панель

Игрок жмёт «Вывести» на предмете в инвентаре → предмет блокируется
(`locked_for_withdrawal`) и создаётся заявка. Дальше заявку ведёт оператор.

### Панель

Откройте `https://<домен>/admin` и войдите по `ADMIN_TOKEN`.

**`ADMIN_TOKEN` обязателен.** Если переменная не задана, сервер генерирует
случайный токен при каждом запуске и печатает его в лог — после рестарта он
меняется. Сгенерировать себе:

```bash
node -e "console.log(require('crypto').randomBytes(24).toString('hex'))"
```

Панель показывает: сколько заявок в каждом статусе, сумма выплат, RTP, число
игроков и открытий кейсов, режим хранилища.

### Жизненный цикл заявки

```
pending  ──(оператор вставил ссылку на trade offer)──▶  ready
pending  ──(оператор отклонил)───────────────────────▶  failed
ready    ──(предмет получен игроком)─────────────────▶  completed
```

| Переход | Что происходит с предметом |
|---|---|
| → `ready` | `trade_ready`, сохраняется ссылка на trade offer |
| → `completed` | предмет **удаляется** из инвентаря — он у игрока |
| → `failed` | предмет возвращается в `available`, его снова можно продать |

Переход `pending → completed` запрещён: завершение удаляет предмет, поэтому без
выданного trade offer игрок потерял бы скин. `completed` и `failed` — конечные
статусы.

Каждый переход создаёт уведомление игроку и отправляется в его открытые вкладки
по WebSocket (`notifications.new`, `inventory.item_status_changed`) — перезагрузка
страницы не нужна.

### Доступ

Два независимых способа:

- **`ADMIN_TOKEN`** — для панели, передаётся в заголовке `X-Admin-Token`.
- **`ADMIN_IDS`** — список аккаунтов (через запятую), которые работают с админ-API
  прямо в игре по обычной сессии. По умолчанию `player_10001`.

Чужие заявки и уведомления не отдаются: `GET /api/withdrawals/:id` отвечает 404,
если заявка не ваша.

### Подписанные сессии

Идентификатор игрока в cookie подписан HMAC-SHA256 и больше не принимается
«как есть». Раньше `Cookie: caser_user_id=player_10001` был полным входом в
админку — теперь нет.

- Секрет хранится в базе (`app_settings`), поэтому переживает деплой. Можно
  задать и вручную: `SESSION_SECRET=<длинная случайная строка>`.
- Старые неподписанные cookie принимаются ограниченное время, чтобы никто не
  потерял свой аккаунт при обновлении: `SESSION_LEGACY_DAYS` (по умолчанию 14).
  Дедлайн записывается один раз и не сдвигается.
- Аккаунты оператора через неподписанную cookie не пускаются. Единственное
  исключение — первый запрос после обновления: браузер оператора один раз
  «привязывается» и получает подписанную cookie.
- Клиент хранит подписанный токен в `localStorage` и присылает его как
  `Authorization: Bearer ...`, так что потеря cookie больше не обнуляет аккаунт.

### Ограничение частоты запросов

Чувствительные маршруты (топ-ап, промокод, открытие кейса, `/api/auth/session`)
имеют лимит на посетителя; сверху — общий лимит 240 запросов в минуту на путь.
Запросы с самой машины (loopback) не считаются: там работают health-check и
тесты. Проверить лимитер локально: `RATE_LIMIT_STRICT=1`.

## 🎰 RTP и маржа казино

`RTP` (Return to Player) — доля ставок, возвращаемая игроку. По умолчанию
**0.80**, то есть казино оставляет **20%**. Меняется одной переменной окружения.

```bash
RTP=0.80   # казино в плюсе на 20%
RTP=0.90   # мягче для игрока
```

### Кейсы

Настоящий caser.one **не публикует** шансы дропа: в его API (`/game/cases/:slug`)
есть только `id`, `marketName`, `price`, `image` — ни `chance`, ни `odds`. Скопировать
неоткуда, поэтому распределение выведено под RTP: вес предмета `price^(-beta)`,
где `beta` подбирается бинарным поиском так, чтобы матожидание выплаты равнялось
`RTP * цена кейса`. Равномерное распределение не годится — на части кейсов оно
даёт RTP выше 100%.

### Апгрейд — формула оригинала

Формула колеса вытащена из бандла настоящего сайта
(`_next/static/chunks/2mwsxxmwyqhg9.js`):

```js
chance%    = clamp(stake / targetPrice * MULT, 1, 80)
superDrop  = rawChance < 1 || rawChance >= 80
null       — шанс не показывается, если targetPrice <= суммы выбранных предметов
50         — при нулевой ставке
```

У оригинала `MULT = 103`. Это **плюс игроку** (RTP 103%) — live-сайт крутит колесо
в минус себе, чтобы люди не уходили.

Здесь `MULT = RTP * 100`, то есть 80: та же формула, но казино в плюсе. Число,
которое видит игрок, равно реальной вероятности броска — обманывать нечем,
и при `MULT <= 80` потолок 80% никогда не срабатывает.

| Ставка / цель | Клон (80) | Оригинал (103) |
|---|---|---|
| 10% | 8% | 10.3% |
| 25% | 20% | 25.75% |
| 50% | 40% | 51.5% |
| 75% | 60% | 77.25% |
| 100% | 80% | 80% (потолок) |

Вернуть оригинальные числа: `UPGRADE_MULTIPLIER=103`.

## ⚡ Особенности реализации

1. **Точная верстка и стили (1:1)**:
   - Полный стек стилей Next.js / Tailwind с CSS-переменными темы бренда (`--brand-accent: #44C987`).
   - Оригинальные векторные и растровые ассеты, фирменные шрифты (`Oswald`, `Sofia Sans`, `Noto Sans`, `Rubik`, `Exo 2`, `DS-Digital`).
2. **Интерактивные разделы**:
   - **Апгрейды (`/ru`)**: центральный верстак с барабаном, выбор желаемых скинов, расчет шансов, live drop лента слева.
   - **Кейсы (`/ru/cases`)**: 151 кейс CS2 по категориям (Ножевые, Перчатки, Армейские и др.).
   - **Награды (`/ru/rewards`)**: розыгрыши «Каждый час», «Каждый день», «Каждую неделю» с таймерами и «Еженедельный набор».
   - **Инвентарь (`/ru/inventory`)**: фильтрация, сортировка по новизне и стоимости.
   - **Юридические страницы**: TOS, Политика конфиденциальности, Cookie, AML, Контакты.
3. **Реальный WebSocket сервер (`/api/ws`)**:
   - Динамический онлайн (флуктуация вокруг реальных ~3850–3890 игроков).
   - Живая лента дропов скинов CS2 в реальном времени.
4. **Встроенный Fallback Proxy**:
   - При любых непредвиденных динамических запросах сервер автоматически кэширует оригинальные файлы с CDN источника.
